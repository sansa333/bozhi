# 设计、harness 与业务补充

## 为什么采用受控工作流

账单操作有明确顺序。让模型自由决定写入、匹配和重试不利于证明结果正确。本项目采用 LangChain Runnable 组织解析、模型提取与验证阶段，金融字段更新由普通 Python 规则控制。智能体能够根据格式选择解析器、识别字段、纠错重试、检查既有账单并输出操作建议；没有赋予它任意运行代码或直接写入账本的工具。

```mermaid
flowchart LR
  A[文件与邮件] --> B[格式解析和来源登记]
  B --> C[指定 OCR 或预览解析]
  C --> D[LangChain 模型抽取]
  D --> E[Schema 和逐字段证据验证]
  E --> F[费用标准化与财务校验]
  F --> G[已有账单匹配与授权更新]
  G --> H[同批重复和冲突检查]
  H --> I[标准 JSON 与待审核记录]
```

## Harness 的具体实现

1. 输入限制。限制单文件、批次、附件数量、递归深度、页数和文本长度。Office 压缩包检查展开大小。不静默截断长文档，截断会待审核。
2. 明确输出合同。抽取对象和账单对象分开。额外字段、非法金额、非有限数字不允许进入已验证数据。实际 JSON 使用 Decimal 序列化，金额不会变成字符串。
3. 逐字段证据。要求模型提供来源中的准确引文，校验值能在引文中找到。路径可做有限格式兼容，但不能擅自修改引文去适配模型输出。证据存在不等于语义必然正确，因此仍保留角色歧义和业务审核。
4. 有限修复。模型最多调用配置次数，SDK 隐式重试关闭。第一次 Schema 或证据验证失败，将字段路径反馈给模型，要求重新提取；失败不丢记录，输出待审核。
5. 决策隔离。模型不能直接执行 CREATE/UPDATE。更改只接受明确允许的字段，检查修改语句包含字段名称和新值，保存原值，再验证合并结果。
6. 业务校验。检查费用金额、币种、数量单价、小计、税额、总计、重复来源、同批不同金额、同名多行及多重匹配。指定 OCR 和模型的费用名称、金额及行数独立核对。金额 O/0、I/1 有规则检查；图像中的可疑编号置空并保留候选值，不自动替换。PP/CC 与到期付款条款分别理解。
7. 可重放运行。保存输入 SHA256、父子来源、解析方式、模型名、提示词版本和摘要、抽取快照、OCR 原始响应、耗时和失败类型。可替换为 ReplayExtractor 重跑规则，避免把模型变化和规则变化混在一起。
8. 明确评测范围。离线测试验证确定性规则及异常处理；原始材料仅完成有限金额核查。另按用户授权建立 14 个多格式合成场景，逐字段检查并区分正确识别和安全拒答，保存真实服务抽取及可重放记录。合成主体和旧账不能冒充用户的实际业务身份和历史账本。
9. 发布检查。提供 pytest、ruff、CI、锁定依赖和白名单打包脚本。打包不收集私人运行目录、密钥和原材料，避免把候选人的本地数据放进交付包。

## 至少五点补充思考

1. 记账主体应由调用方明确提供。邮件发件人、文件签发人、收款人可能不同，平台 Logo 也可能只代表制单软件。一个业务可同时产生面向客户的应收与面向供应商的应付，不能只保留全局唯一方向。
2. 行级唯一标识比费用名更重要。提供的材料中存在两条同名、不同金额的 Handling Charge。只有单据号和名称时，更新目标可能不唯一。生产接口应补充费用行 ID、税率、箱型、计费单位和业务段。
3. Credit Note 需要原单关联与会计政策。客户贷项与供应商贷项分别冲减不同科目，资金流向和科目分类不能混为一谈。默认待确认；配置关联原单冲减政策后，要求唯一原单、相同主体及交易双方、有效币种与可冲减余额，保留原单 AR/AP，并保存原始金额和负金额转换依据。重复贷项和同批多笔冲减分别检查。
4. 单据类型与金额真实性需要区分。到货通知可能包含实际待付费用，也包含条件性罚款、费率、重量和银行账号。应按版面和上下文识别真实费用区，不能用全文金额正则生成账单。
5. 合计应按币种与税务口径分别校验。同一费用可能同时显示原币和本位币金额，不应双计。数量、单价与总额的舍入精度应配置为币种和计费单位规则，目前使用 0.01 作为候选核验容差，不能视为适用于所有币种。
6. 修改邮件需要时间和权限信息。仅发现数字变化不足以覆盖历史账单。生产系统还需授权发件人、Message-ID、版本顺序、原始签名和人工批准。当前只产生更新建议，不执行真实账本写入。
7. 幂等需要业务数据库支持。来源 SHA256 可处理相同字节重传，但转格式后摘要会变化。系统提供稳定 ingestion ID 和同批检查，生产数据库还应使用业务唯一键、版本检查和事务，避免多人并发审批导致重复入账。
8. 置信度要经评测校准。模型自报 1.0 不代表事实正确。当前低置信度阈值只是保守筛选；证据缺失、合计不平和多重匹配拥有独立阻断权。后续应按字段使用独立标注集测准确率与拒答覆盖率。
9. OCR 返回结果必须先核实。本轮合成费用实测确认 chargeList 中的 chargeItem、amount 和 chargeCtr，服务未提供原始文字或该费用的币种。保留响应，从原文件取得独立证据，按名称和金额逐行对照。未观察到的税额、付款方式和置信度字段不擅自解释。接口不支持的 TIFF 先逐帧转 PNG，仍调用指定接口。
10. 数据托管和删除策略需要调用方决定。OCR 的公网 URL 可用短期签名，但服务必须在有效期内下载。运行目录有单据文字和交易信息，应使用受控存储、磁盘权限、加密与保留期策略，不应把材料默默上传到任意第三方。

## 交付边界

本项目是可运行的笔试实现，所有 CREATE/UPDATE 都是操作建议。财务系统连接、人工审批写入、并发事务、租户权限、币种专属舍入策略、生产隔离、文档病毒扫描和历史账本迁移需要明确接口与业务合同后再建设。
